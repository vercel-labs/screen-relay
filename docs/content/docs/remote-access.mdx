---
title: Remote access
description: Open the viewer or control a session from another machine with an SSH tunnel, a public HTTPS URL, or native TLS.
---

Open a session's viewer and run its client commands from another machine. A session listens on `127.0.0.1:8080` by default, including when you pass `--public`. It stays on loopback unless you pass `--bind`, so a proxy or client that connects without a tunnel needs an address it can reach. Anyone with a session's token can see and control its desktop. A session has one token and no user identity. To share less than that, create a [grant](#grants).

## Choose a path

| Path | Use it when | Listen address | Token |
| --- | --- | --- | --- |
| SSH tunnel | You have SSH access to the VM. | `127.0.0.1` (default) | None on Linux; required on macOS and Windows |
| Behind a TLS proxy | A cloud sandbox port, nginx, Caddy, or a tunnel forwards to the VM. | `127.0.0.1` for a proxy on the VM; otherwise an address the proxy can use | Required |
| Native TLS | Clients connect straight to the VM and you have a certificate. | An address clients can use, such as the VM's public address | Required |

## SSH tunnel

1. On your machine, open the tunnel:

   ```sh
   ssh -N -L 8080:127.0.0.1:8080 user@your-vm
   ```

2. Open `http://127.0.0.1:8080`, or the viewer link that `up` printed when the session has a token.

The session stays on loopback, so the tunnel reaches it without a public URL. Linux sessions need no token; macOS and Windows sessions always have one.

## Behind a TLS proxy

1. On the VM, start the session with the public origin:

   ```sh
   screen-relay up -d --public https://desktop.example.com
   ```

   `--public` takes a bare HTTPS origin, sets the accepted public host, and creates a token. It does not change the listen address. Use the configured HTTPS URL for remote access. The built-in viewer still works on the same loopback address, including through an SSH tunnel. See [Browser origins](#browser-origins) for embedded viewers.

2. Configure the proxy to:
   - forward every path with no prefix, including `/viewer.js`, `/stream`, `/control`, and the `/rtc` endpoints ([endpoints](/docs/protocol#endpoints))
   - forward WebSocket upgrades over HTTP/1.1
   - pass `Host`, `Origin`, and `Authorization` through unchanged, and keep the WebSocket subprotocol header
   - keep `Authorization` and the subprotocol header out of its logs, because the token travels in both

3. Open the viewer link that `up` printed.

Without `--tls-cert`, the engine serves plain HTTP and the proxy terminates TLS. A proxy on the same VM can use `127.0.0.1`. For a proxy that runs elsewhere, pass `--bind` with an address only the proxy can reach. Do not expose that port to clients. The engine ignores `X-Forwarded-*` headers.

`up` prints a `TLS proxy` row that names the forwarding target.

## Native TLS

1. On the VM, start the session with your certificate:

   ```sh
   screen-relay up -d --bind 0.0.0.0 --tls-cert fullchain.pem --tls-key key.pem --public https://desktop.example.com
   ```

2. Open the viewer link that `up` printed.

The engine serves HTTPS itself, prints no `TLS proxy` row, and speaks HTTP/1.1 only. This example listens on all IPv4 interfaces. Pass a specific address to `--bind` if only one interface should accept connections. Client commands on the VM accept the session's own certificate even when its host name does not match, so a self-signed certificate works there.

## Browser origins

A browser sends an `Origin` header on WebSocket connections and on cross-origin requests, naming the page that made them. The engine checks that header in addition to the token, so a page on another site cannot use a token it obtained.

| Session | Origins the engine accepts |
| --- | --- |
| Started with `--public` | The `--public` origin, each origin in `--allow-origin`, and a loopback page whose origin uses the same `HOST:PORT` it connects to, such as `http://127.0.0.1:8080`. |
| Started without `--public` | Loopback origins (`http` or `https`, `localhost` or `127.0.0.1`, any port), and each origin in `--allow-origin`. |

A request from any other origin gets 403 `forbidden`, and a WebSocket fails its handshake. The CLI, the Node SDK, and other clients that send no `Origin` header are not affected. A WebSocket that uses a [grant](#grants) skips this check, so a viewer embedded on an opaque or changing origin, such as in an MCP App host, can connect with a grant. An HTTP request that uses a grant does not skip the check.

To let a page on another origin connect, such as an app that embeds the viewer, list its origin when you start the session:

```sh
screen-relay up -d --public https://desktop.example.com --allow-origin https://app.example.com
```

A page that a local app serves, such as an embedding host on this machine, can connect from a loopback HTTP origin:

```sh
screen-relay up -d --public https://desktop.example.com --allow-origin http://localhost:8081
```

- Separate several origins with commas and no spaces, up to 16. You can set `SCREEN_RELAY_ALLOW_ORIGIN` or `server.allow_origin` instead of the flag.
- Write each origin the way the browser sends it: lowercase `https://HOST[:PORT]` for any host, or `http://localhost[:PORT]` or `http://127.0.0.1[:PORT]` for a page served on the machine itself. Use no path and no trailing slash. Leave out port 443 for HTTPS and port 80 for HTTP.
- The engine compares the whole string. It has no wildcard, so `https://app.example.com` does not cover `https://www.app.example.com`.
- `--allow-origin` creates a token even when the session listens on `127.0.0.1`, and the allowed page must send it.
- The engine never accepts `Origin: null`, which a browser sends from a sandboxed frame or a `file://` page.

### Embedded viewers and CORS

A page on an allowed origin can open the WebSocket stream. The engine checks the `Origin` header during the WebSocket handshake, and browsers do not apply CORS to WebSocket connections, so the stream works from another origin once you allow it.

Browser HTTP requests do follow CORS. The engine sends no `Access-Control-Allow-Origin` header, so a page on another origin cannot read `/capabilities`, `/metrics`, `/screenshot.png`, `/rtc/config`, or the clipboard endpoint, and cannot send `POST /rtc`, even when `--allow-origin` lists it. Serve the viewer from the relay origin when it needs those endpoints. An embedded viewer that only uses the WebSocket works from an allowed origin.

### Update an app that connects from another origin

Earlier versions accepted any origin when the session had a token. A session with `--public` now refuses a page on another origin until you allow that origin. The built-in viewer still works on loopback when its origin uses the same `HOST:PORT` it connects to, such as `http://127.0.0.1:8080` through an SSH tunnel. Use `--allow-origin` for an embedded viewer on another origin. This enables its WebSocket connection, not cross-origin browser access to the HTTP API.

For an embedded viewer, including an MCP App inside an AI client, allow the origin of the page that opens `/stream`:

1. Find the origin the app's page runs on. In the browser's or client's developer tools, open the failed `/stream` request and read its `Origin` request header.
2. Restart the session with that value in `--allow-origin`. A loopback value such as `http://localhost:8081` is accepted. Restarting creates a new token, so give the app the new one.
3. Reload the app.

If the header is `null`, the client renders the app in a frame without an origin of its own, and the app cannot connect from the browser. Route its requests through a server you control, which sends no `Origin` header and holds the token.

## Tokens

screen-relay creates a 64-character lowercase hex token (256 random bits) whenever the session listens anywhere other than `127.0.0.1`, uses `--public` or `--allow-origin`, or runs on macOS or Windows.

- The token is stored in a `token` file in the session's state directory, readable only by its owner. `screen-relay status --json` shows the path as `tokenFile`.
- `screen-relay status` hides the token unless you pass `--show-token`.
- The viewer reads `#token=` from the link that `up` prints, removes it from the address bar, and uses it only on `https://` or loopback pages. Browsers never send the fragment to the server.
- Each `screen-relay up` creates a new token and ends open connections. To rotate a token, run `screen-relay down`, then `screen-relay up`.

## Grants

Grants replace the one-time `/tickets` endpoint introduced in v0.1.2. Custom viewers now send `bearer.GRANT_TOKEN` instead of `ticket.TICKET`.

A grant gives someone part of a session for a limited time without giving them the token. You create it with the token, and you can revoke it before it expires.

| Scope | What the holder can do |
| --- | --- |
| `watch` | Watch the desktop over a WebSocket or a WebRTC session. |
| `control` | Watch the desktop and send input, in the viewer, over `/control`, or over a WebRTC session. |

Neither scope can read or set the clipboard, take a screenshot over HTTP, send `POST /input`, or create and revoke grants. A grant can call `GET /rtc/config`, `POST /rtc`, and `DELETE /rtc/session` or `DELETE /rtc/sessions/ID` for the session it created. No other HTTP endpoint accepts a grant. A WebRTC session opened with a grant receives no clipboard notices.

1. Create the grant from a machine that has the token. This example creates a watch grant that lasts 10 minutes. Without `ttl`, a grant lasts 3600 seconds, which is also the maximum.

   ```sh
   curl -s -X POST -H "Authorization: Bearer $(cat ./token)" "https://desktop.example.com/grants/watch?ttl=600"
   ```

   The response has this shape:

   ```json
   {"id":"ID","token":"GRANT_TOKEN","expires_in":600,"scope":"watch"}
   ```

   Use `/grants/control` for a control grant.

2. Build the viewer link from the grant's `token` and share it:

   | Scope | Link |
   | --- | --- |
   | `watch` | `https://desktop.example.com/#token=GRANT_TOKEN&scope=watch` |
   | `control` | `https://desktop.example.com/#token=GRANT_TOKEN&scope=control` |

   The viewer removes the fragment from the address bar, as it does for the session token. A watch link shows the desktop with no **Take control** button. A control link can take and release control, but it has no clipboard sync, and its stats panel shows no engine metrics.

3. To end the grant early, revoke it with its `id`:

   ```sh
   curl -s -X DELETE -H "Authorization: Bearer $(cat ./token)" "https://desktop.example.com/grants/ID"
   ```

Add `connections=1` to create a grant that opens only one connection, either a WebSocket or a WebRTC session, such as `?ttl=120&connections=1`. The connection stays open, and while a WebRTC session connects or stays open, the grant can still end that session. If the session ends before it connects, the grant is released, so the viewer can fall back to a WebSocket. Once a connection opens, a copied link can no longer connect: the engine refuses the WebSocket handshake, and `/rtc/config` or `POST /rtc` returns `401`.

When a grant is revoked or expires, the engine closes the connections opened with it and refuses new ones. Other viewers and clients stay connected. Grants are kept in memory, so `screen-relay down` ends them all.

A custom client sends the grant's `token` as `bearer.TOKEN` on a WebSocket and as `Authorization: Bearer TOKEN` on a WebRTC HTTP request. The [protocol](https://github.com/vercel-labs/screen-relay/blob/main/PROTOCOL.md#grants) lists the WebSocket and WebRTC access each scope has.

## Control a session from your laptop

1. On your laptop, install the CLI. It needs Node 22 or newer and runs on any OS:

   ```sh
   npm install -g screen-relay
   ```

2. On the VM, run `screen-relay status --show-token`. On your laptop, save the token in a new private directory. In a POSIX shell, run the following, paste only the token, press Enter, then press Ctrl+D:

   ```sh
   if relay_token_dir=$(mktemp -d "$HOME/.screen-relay-token.XXXXXX"); then
     (umask 077; cat > "$relay_token_dir/token")
   fi
   ```

   Keep the token private. Delete the file and its directory when you no longer need them.

3. In the same shell where you saved the token, set the target and run client commands:

   ```sh
   export SCREEN_RELAY_URL=https://desktop.example.com
   export SCREEN_RELAY_TOKEN_FILE="$relay_token_dir/token"
   screen-relay status
   screen-relay screenshot screen.png
   ```

To pass the URL and token per command, use `--url` and `--token-file` instead. Use HTTPS for any remote host. Plain HTTP works only for `localhost` or `127.0.0.1`, and redirects are not followed. The [CLI reference](/docs/cli#client-target) lists the URL rules. In Node, pass the same URL and token to `createClient` ([SDK options](/docs/sdk#options)).
