Call screen-relay over HTTP from any language. For most tasks, use the [CLI](/docs/cli) or [Node SDK](/docs/sdk).

## Read the screen

Start a session, then run these commands on the VM or through an [SSH tunnel](/docs/remote-access#ssh-tunnel):

```sh
curl -fsS http://127.0.0.1:8080/capabilities
curl -fsS http://127.0.0.1:8080/screenshot.png -o screen.png
```

These commands assume the default address and a session bound to `127.0.0.1` without `--public`. That session has no token.

For a session with a token:

1. Run `screen-relay status --json` on the VM to find its `tokenFile` path. Add `--name NAME` for a named session.
2. Replace `/path/to/token` with that path, and add `-H "Authorization: Bearer $(cat /path/to/token)"` to each request.
3. Use the HTTPS origin if the session uses TLS.

## Send input

<span id="input-events" />
<span id="input-records" />

Close a control session, or a viewer that owns input, before sending HTTP input. A view-only viewer does not block input. Then send input from any machine with the [CLI](/docs/cli), passing `--url` and `--token-file`, or with the [Node SDK](/docs/sdk).

```sh
screen-relay click 0.5 0.5 --url https://desktop.example.com --token-file ./token
```

Replace the URL and [save the session token in a private file](/docs/remote-access#control-a-session-from-your-laptop), and pass that file in place of `./token`. For a local session, omit `--url` and `--token-file`. Text input uses the desktop's keyboard layout and can type characters absent from it.

`POST /input` takes binary records. To write your own client, see the [wire protocol](https://github.com/vercel-labs/screen-relay/blob/main/PROTOCOL.md).

## Read and set the clipboard

`GET /clipboard` returns the desktop's clipboard text as `{"text":"…"}`, and an empty string when the clipboard holds no text. `POST /clipboard` replaces it with the request body, read as UTF-8 text:

```sh
curl -fsS http://127.0.0.1:8080/clipboard
curl -fsS --data-binary 'Hello from the API' http://127.0.0.1:8080/clipboard
```

A write returns `{"length":N}`, the number of bytes set, and an empty body clears the clipboard. The clipboard works while another client owns input, like a screenshot. Text is limited to 256 KiB and cannot contain NUL characters. To paste the text into an app, send the paste keys afterward, such as `screen-relay key ctrl+v`.

`capabilities.clipboard` is `true` when the desktop has a clipboard the engine can use. On Wayland, the compositor must support the wlr-data-control protocol, which sway and labwc do.

## WebRTC viewers

A viewer link carries the transport in its fragment:

| Fragment | Behavior |
| --- | --- |
| `#transport=auto` | Starts on the WebSocket stream at once, then upgrades to WebRTC in the background when the engine offers it and ICE succeeds. This is the default. |
| `#transport=rtc` | Connects over WebRTC and falls back to the WebSocket stream when WebRTC fails. |
| `#transport=rtc-only` | Connects over WebRTC only, with no fallback. A failed connection ends the stream. |
| `#transport=ws` | Uses the WebSocket stream only. |

Every viewer shares one encoder, so a WebRTC viewer joins the stream already running for the others. Each WebRTC viewer has its own session, so several can connect to one engine at once.

WebRTC uses the servers from `server.ice_servers` or `--ice-server`. The flow is:

1. `GET /rtc/config` returns `{"enabled":true,"iceServers":[{"urls":"stun:stun.example.com"}]}`. `enabled` is `false` when the engine was built without WebRTC. The session token or a grant can call it.
2. `POST /rtc` with the SDP offer as `application/sdp` returns `201` with the answer SDP and a `location` header such as `/rtc/sessions/ID`. The session token or a grant can call it. Add `?view=1` to open a view-only session.
3. `DELETE /rtc/sessions/ID` ends that session. The session token can replace or end any session. A grant can replace or end only the session it created, and `DELETE` on any other session returns `403`. `DELETE /rtc/session` ends the caller's current session and remains as an alias for older clients.

Each WebRTC session has an `events` data channel that carries cursor updates and viewer ACKs. A session opened with the session token also receives clipboard notices. A WebRTC viewer sends input over its `input` data channel while no other client owns input. A watch grant opens a view-only session, a control grant opens a session that can send input, and a grant-backed WebRTC session closes when its grant expires or is revoked. A failed offer returns `400` or `503` with an `error` field. The [Errors](#errors) table lists the reasons.

## Endpoints

When the session has a token, the endpoints that return session data require the session token, except that a grant's `token` also works on `GET /rtc/config`, `POST /rtc`, `DELETE /rtc/session`, and `DELETE /rtc/sessions/ID`. The WebSocket endpoints accept the session token or a grant's `token`.

| Method | Path | What it does |
| --- | --- | --- |
| `GET` | <span id="get-capabilities" />`/capabilities` | Returns the desktop size, backend, features, and input limits as JSON. |
| `GET` | `/screenshot.png` | Returns a PNG without the cursor, even when another client owns input; maximum 8 MiB and a 5-second timeout. |
| `POST` | <span id="post-input" />`/input` | Sends a batch of binary input records. |
| `GET`, `POST` | <span id="clipboard" />`/clipboard` | Reads or replaces the clipboard text. |
| `GET` | <span id="get-metrics" />`/metrics` | Returns stream and resource metrics as JSON. |
| `GET` | <span id="get-rtc-config" />`/rtc/config` | Returns whether WebRTC is available and the ICE servers a viewer should use. The session token or a grant can call it. |
| `POST` | <span id="post-rtc" />`/rtc` | Exchanges an SDP offer for an answer and opens a WebRTC session. Add `?view=1` for a view-only session. The session token or a grant can call it. |
| `DELETE` | <span id="delete-rtc-session" />`/rtc/sessions/ID` | Ends the WebRTC session with that `id`. The session token can end any session. A grant can end only the session it created; any other session returns `403`. `DELETE /rtc/session` ends the caller's current session and stays as an alias. |
| `POST` | <span id="post-grants" />`/grants/watch`, `/grants/control` | Creates a [grant](/docs/remote-access#grants): a credential limited to watching, or to watching and input. Add `?ttl=SECONDS`, up to 3600, which is also the default, and `connections=1` for a grant that opens one connection. Returns `id`, `token`, `expires_in`, `scope`, and `connections` for a single-connection grant, as JSON. |
| `DELETE` | <span id="delete-grants" />`/grants/ID` | Revokes the grant with that `id` and closes the connections opened with it. Returns 200. |
| `GET` | `/`, `/index.html`, `/viewer.js` | Serves the viewer. |
| WebSocket | `/stream` | Streams video and cursor images when supported. With no query parameter, it claims idle input. Use `?view=1` to watch without input or `?take=1` to take input from the current owner, which closes with code 4001. Add `clipboard=1` to a claiming or takeover stream to receive clipboard notices. |
| WebSocket | `/control` | Sends input and receives a response for each event, without video. It can run next to a view-only `/stream`, and closes with code 4001 when a viewer takes control or code 4003 when it connects while input is owned. |

`/capabilities` also reports `encoder`, the name of the active encoder; `hardware_encoder`; `encoder_state`, one of `uninitialized`, `probing`, `hardware_active`, `hardware_degraded`, `software_active`, or `failed`; `rtc`, which is `true` when the engine offers WebRTC; `ice_servers`, the number of configured STUN and TURN servers; and `transfer_tier`, one of `zero_copy`, `dirty_upload`, `full_upload`, or `software`, which names how captured frames reach the encoder.

The viewer HTML is served with `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, so another site cannot embed it and forward clicks to the desktop.

The engine sends no CORS headers. A browser page on another origin can open a WebSocket when its origin is allowed, but the browser blocks its HTTP requests, including `/capabilities`, `/metrics`, `/screenshot.png`, and `/rtc/config`. See [Embedded viewers and CORS](/docs/remote-access#embedded-viewers-and-cors).

## Authentication

- When the session has a token, send `Authorization: Bearer TOKEN` for HTTP requests, or offer `bearer.TOKEN` as a WebSocket subprotocol. Do not put the token in a request URL. See [Tokens](/docs/remote-access#tokens).
- A grant's `token` works in place of the session token on the WebSocket endpoints and on the WebRTC HTTP endpoints. Send it as `bearer.TOKEN` for a WebSocket and as `Authorization: Bearer TOKEN` for an HTTP request. A watch grant opens `/stream?view=1` and view-only WebRTC sessions. A control grant opens `/stream`, `/stream?take=1`, `/stream?view=1`, and `/control`, and WebRTC sessions that can send input, or view-only sessions with `POST /rtc?view=1`. Neither opens a URL with `clipboard=1`, and neither receives clipboard notices on the WebRTC `events` data channel.
- For HTTP requests, a grant authorizes only `GET /rtc/config`, `POST /rtc`, `DELETE /rtc/session`, and `DELETE /rtc/sessions/ID`. `/clipboard`, `/input`, `/screenshot.png`, `/capabilities`, `/metrics`, and `/grants` still need the session token. A grant WebSocket connects from any origin, including `null`. An HTTP request that uses a grant follows the same `Host` and `Origin` rules as the session token. See [Grants](/docs/remote-access#grants).
- The `Host` must be `localhost`, `127.0.0.1`, or the authority configured with `--public`, with its port if specified. For the `--public` authority, an uppercase host name and port 443 are normalized before the comparison.
- `Origin` is optional. Requests without it still need an accepted `Host` and any required token. If present, `Origin` must match the configured `--public` origin, an entry in `--allow-origin`, or a loopback origin whose host and port match the loopback `Host` header. Without `--public`, loopback origins on other ports are also accepted. Other values, including `null`, are rejected. A grant WebSocket is the exception; it connects from any origin. See [Browser origins](/docs/remote-access#browser-origins) for accepted formats and browser HTTP limits.

## Errors

<span id="limits" />

| Status | What to do |
| --- | --- |
| 400 `invalid_input` | Send a nonempty batch of valid records with the correct `Content-Length`. |
| 400 `invalid_text` | Send clipboard text as UTF-8 without NUL characters. |
| 400 `invalid_offer` | Send a valid SDP offer with a `Content-Length` from 1 byte to 64 KiB. |
| 400 `invalid_query` | Use a supported query parameter. `POST /rtc` accepts only `view=1`; grant requests accept `ttl` and `connections=1`. |
| 400 `no_h264` | Send an SDP offer that includes an H.264 video codec. |
| 401 `unauthorized` | Send the correct session token or grant token. An expired grant, or a used single-connection grant that tries to open another connection, also returns this status. |
| 403 `forbidden` | Check the `Host` and `Origin` rules under [Authentication](#authentication). A grant that tries to end a WebRTC session it did not create also gets this status. |
| 404 `not_found` | Check the endpoint path. |
| 405 `method_not_allowed` | Use the method listed for the endpoint. |
| 409 `busy` | Close the input owner or wait, then check for partial input before retrying. A viewer that owns input is one owner; a view-only viewer is not. Another WebRTC offer in progress also returns `busy`. |
| 411 `length_required` | Include `Content-Length` on `POST /input` and `POST /clipboard`. |
| 413 `too_large` | Send no more than 256 input records per request or 256 KiB of clipboard text. |
| 413 `clipboard_too_large` | The clipboard holds more than the 256 KiB read limit. |
| 422 `unsupported_input` | Change the input or keyboard layout. |
| 503 `busy` | Wait for the other screenshot request to finish. |
| 503 `rtc_busy` | Send the offer again. The engine interrupted the previous offer before its body arrived. |
| 503 `rtc_failed` | The WebRTC session failed to gather or connect. Send the offer again. |
| 503 `rtc_timeout` | The WebRTC session did not answer in time. Send the offer again. |
| 503 `no_answer` | The engine produced no SDP answer. Send the offer again. |
| 503 `viewer_limit` | Close a viewer, then retry the WebRTC offer. |
| 503 `capture_unavailable` | Check `screen-relay logs engine` and retry the WebRTC offer. |
| 503 `clipboard_busy` | Wait for the clipboard request queue to drain, then retry. |
| 503 `clipboard_unavailable` | The desktop has no clipboard the engine can use, or the app that owns the clipboard did not answer within 2 seconds. Check `capabilities.clipboard`. |
| 503 `screenshot_unavailable` | Check `screen-relay logs engine` and try again. |

Errors are JSON with an `error` field.

- A rejected input record returns its zero-based `index`. The records before it were applied, and that record and the ones after it were not.
- A `busy` input reply returns an `applied` count. Text-only input can resume from it. For other input it is not a retry offset, because the engine drops queued text, pointer moves, and scrolls but still applies key and button events. Check the desktop before retrying.
